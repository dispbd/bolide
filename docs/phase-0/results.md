# Фаза 0: итоги

Цель фазы: проверить, что изоморфный мутатор (один код на клиенте и сервере) даёт optimistic UI поверх Hono + TanStack DB + ElectricSQL, замерить задержки и размер бандла, решить вопрос ядра.

## Что сделано

- `spike/core/mutator.ts`: `defineMutator`, `mutatorRegistry`, общий интерфейс `MutatorTx`, валидация через Standard Schema.
- `spike/core/recording-tx.ts`: клиентская транзакция. Читает из локального стора, видит свои же записи, записывает операции.
- `spike/server/`: Hono-сервер. `POST /api/mutate` выполняет тот же мутатор в транзакции Postgres и возвращает `txid`; `GET /api/shape/:table` проксирует Electric.
- `spike/core/client.ts`: клиент. Мутатор применяется к коллекциям TanStack DB сразу, затем уходит на сервер; транзакция завершается, когда `txid` пришёл обратно через Electric. Отказ сервера откатывает изменение.
- Тесты: 6 юнит-тестов и 3 интеграционных на двух клиентах через настоящий Electric (создание, переключение, отказ с откатом). Все проходят.

## Замеры

Localhost, Node 22, Postgres 16, Electric 1.8.1, 200 итераций. Сеть до сервера здесь почти нулевая; в реальности к «подтверждению» прибавится RTT, а к optimistic ничего.

| Что | p50, мс | p95, мс | p99, мс |
|---|---|---|---|
| Изменение видно в UI (optimistic) | 0.42 | 0.95 | 1.81 |
| Подтверждено: запись вернулась через Electric | 7.26 | 12.52 | 25.47 |
| Базовая линия: обычный POST без синхронизации | 5.21 | 9.88 | 12.81 |

Вывод: UI реагирует меньше чем за 1 мс независимо от сети. Цена синхронизации сверху обычного запроса около 2 мс на p50.

| Бандл | min, КБ | min+gzip, КБ |
|---|---|---|
| Клиент целиком (TanStack DB + Electric + zod + мутаторы) | 657.9 | 157.0 |
| из них TanStack DB + electric-collection | 211.3 | 64.6 |
| из них @electric-sql/client | 54.3 | 17.3 |
| из них zod (одна схема) | 443.3 | 91.2 |
| для сравнения: zod/mini (та же схема) | 14.5 | 5.1 |
| Сервер (Hono + наш код, без драйвера postgres) | 19.9 | 8.3 |

Вывод: больше половины клиента занимает полный `zod`. С `zod/mini` или Valibot клиент будет около 70 КБ gzip, это в три раза меньше клиента Zero (около 230 КБ). Сервер весит 8 КБ gzip.

## Что выяснилось

1. **Модель работает без доработок библиотек.** Достаточно `createTransaction` из TanStack DB и `awaitTxId` из Electric. Своего sync-движка на этом этапе не нужно.
2. **Имена мутаторов должны быть литеральными типами**, иначе типизация `mutate()` теряется. Решено через `mutatorRegistry(...)`.
3. **Правила, которые клиент не может проверить** (владелец записи), естественно ложатся на `tx.side === 'server'`. Клиент показывает изменение, сервер отклоняет, UI откатывается. Это проверено тестом.
4. **Права на чтение пока не реализованы.** Прокси шейпов есть, но фильтра по пользователю нет: любой видит все строки. Это задача фазы 3.
5. **Клиент видит только синхронизированные данные.** Если строки нет в локальном сторе, клиентский прогон мутатора упадёт с `not_found`. Нужен режим «только сервер» для таких мутаторов.
6. **Операционная цена Electric:** отдельный сервис и `wal_level=logical`. Для «лёгкого» фреймворка нужен режим разработки без Docker; кандидат на отдельную задачу.
7. **TanStack DB ещё 0.x**, API меняется (возврат `{ txid }` из обработчиков уже помечен устаревшим). Поэтому клиентский слой держим за своим интерфейсом.
